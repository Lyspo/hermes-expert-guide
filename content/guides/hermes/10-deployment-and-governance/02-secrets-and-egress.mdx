An agent that can run commands and read files is, by construction, an agent that can read
your credentials. This lesson is where they are, which surfaces can see them, and the
feature built specifically to make one surface unable to.

## Which surface sees what

Not one boundary but several, and they differ:

| Surface | What it can see |
|---|---|
| `execute_code` | Variables blocked by name pattern |
| Local terminal | Blocks Hermes's own infrastructure variables |
| Docker | **Nothing by default** — `docker_forward_env` is empty |
| Modal | Credential files mounted in |
| MCP stdio subprocess | Stripped to a safe baseline plus what you named |

The Docker default is the good one and worth not undoing casually: a container inherits
no host environment unless you list what it should get.

Skills can declare `required_environment_variables` and `required_credential_files`, and
declared variables are auto-passed into sandboxes — which is convenient and is also how a
variable ends up somewhere you did not picture it.

MCP errors pass through credential-redaction patterns before reaching the model, so a
failing request does not echo a token back into the transcript.

And from `04/02`, writes to credential locations are refused outright — `~/.ssh/`,
`~/.aws/`, `~/.kube/`, `.netrc`, Hermes's own stores, and `.env` files anywhere.

## Where secrets live

`~/.hermes/.env` is the default home, `chmod 600`.

If you are on Nous Portal the situation is unusually good, and quoted: "The refresh token
at `~/.hermes/auth.json` is the only credential on disk." Short-lived tokens are minted
per request rather than long-lived keys being stored.

For everyone else, v0.19.0 added a secret-source plugin interface with Bitwarden and
1Password implementations — so secrets can live in a manager rather than a dotfile.

## The problem the proxy solves

Here is the exfiltration path, and it is worth stating concretely because it motivates
everything below.

You run the agent in a Docker sandbox for isolation. That sandbox needs to call your
model provider, so it holds `OPENROUTER_API_KEY` as an ordinary environment variable.
Now a prompt-injected agent inside that sandbox runs `printenv | grep -i key`, or reads
a credential file, and walks away with the real thing.

The isolation was real and it protected the wrong asset.

## What it does

The sandbox never holds a real key — only an opaque proxy token. Outbound traffic routes
through `iron-proxy`, a pinned, checksum-verified daemon on the host, which terminates
TLS with a locally generated certificate authority, swaps the token for the real
credential, and forwards upstream.

```bash
hermes egress setup
hermes egress start
hermes egress status
```

Ten provider hosts are allowlisted by default, extensible with wildcards. A deny list of
CIDRs is checked at connect time regardless of the allowlist — loopback, RFC1918,
link-local including **cloud metadata at 169.254.169.254**, IPv6 ULA, CGNAT, and
IPv4-mapped-IPv6, which closes a dual-stack metadata bypass. Because it is enforced at
connect time, DNS rebinding through an allowed hostname cannot reach a private address.

The bind policy is never `0.0.0.0` — the Docker bridge gateway on Linux, loopback on
macOS and Windows. A LAN peer with a stolen token cannot reach it.

<Depth min="operator">

With `credential_source: bitwarden` the daemon refetches secrets on **every start**. So
rotation is: change it in Bitwarden, then `hermes egress stop && start`. No `.env` edit,
no host restart. It fails loudly by default if the fetch returns nothing, with an opt-in
fallback for staged migrations.

**It is Docker-only.** Modal, Daytona, SSH and Singularity receive no proxy environment
and no CA mount, so a sandbox on those backends holds the real keys.

</Depth>

## What it does not do

The documentation states its own limits precisely enough to quote, and the governance
framing is the sentence to carry into a review:

> Compromise the sandbox and the attacker walks away with tokens that only work behind
> the **configured trusted proxy boundary** — the CA private key and the proxy endpoint
> integrity are part of that boundary. If traffic can be redirected to
> attacker-controlled proxy infrastructure... the token guarantee no longer holds.

Seven gaps, published rather than discovered:

1. **A compromised host process.** This is defence in depth for sandbox compromise only.
2. **Loss of the boundary itself** — CA key theft or a hijacked endpoint.
3. **Raw sockets bypassing `HTTPS_PROXY`.** Node is partly mitigated, but code passing
   its own certificate authority to a TLS connection is not covered — a known v1
   limitation.
4. **Credential files mounted into Docker.** The proxy covers environment variables, not
   arbitrary mounts.
5. **Exfiltration to an allowlisted host.** An agent can still put stolen data in a
   request body to an allowed provider. The proxy logs it and does not block it.
6. **AWS Bedrock and GCP Vertex.** SigV4 signing and service-account files are not
   covered — "if their env vars are present, the sandbox holds **real credentials** for
   those providers."
7. **In-memory secret recovery** from the daemon's own process.

<ForTrack track="architect">

Gaps five and six are the ones to act on rather than merely note.

**Five** means the proxy is a credential control and not a data-exfiltration control. If
your threat model includes an agent sending data somewhere it should not, this feature
does not address it, and the request logs are your only signal.

**Six** means the guarantee is provider-dependent. A deployment on Bedrock or Vertex gets
substantially less from this than one on OpenRouter or Anthropic, and any statement of
the form "credentials are isolated from the sandbox" is false for those two.

That the documentation says all of this itself is worth crediting. A control that
publishes its limits is easier to deploy correctly than one that implies completeness.

</ForTrack>

## Two different features with similar names

`hermes egress` is the outbound credential firewall above.

`hermes proxy` is an entirely separate, **inbound** feature — an OAuth-subscription
aggregator. Different direction, different purpose, no relationship.

They are named here together exactly once so that you never conflate them.

## What to take from this

Credentials live in `.env`, or in a secret manager, or — on Portal — barely on disk at
all. Each execution surface sees a different subset, and Docker's default of nothing is
the right one.

The egress proxy removes real keys from the sandbox, which is a genuine and well-built
control with seven published gaps. Two of those matter in practice: it does not stop
exfiltration to an allowed host, and it does not cover Bedrock or Vertex at all.

Most agents you have used are stateless. You describe a task, they work through
it, and when the window closes the reasoning goes with it. Ask the same thing next
week and you pay for the same thinking again.

Hermes keeps three things instead: a record of what it learned about you and your
environment, a library of procedures it wrote for itself, and the ability to hand
work to copies of itself. That combination is the whole claim, and each part is
smaller and more concrete than the writing around it suggests.

## It writes its own procedures

When Hermes finishes something involved, it can write down how it did it. Not a
log — a procedure, in a file, that it will find and follow next time.

<Transcript label="~/.hermes/skills/github/github-repo-discovery/SKILL.md" fidelity="verbatim" source="An agent-authored skill, read from a real v0.19.0 install on 2026-07-25; workflow body elided">
{`---
name: github-repo-discovery
description: Discover under-the-radar GitHub repos via API search.
---

# GitHub Repo Discovery

Use when the user wants to find quality open-source repos that aren't yet
famous — hidden gems, underrated tools, niche frameworks, or emerging
projects with real substance but modest star counts.

## Workflow
  …

## Pitfalls

- **\`language\` can be null.** Always use \`item.get('language') or '?'\` — a
  bare \`{lang}\` format string crashes on \`None\`.`}
</Transcript>

Two fields of frontmatter, a sentence saying when to use it, a workflow, and a list of
things that went wrong. Nobody wrote that file. Hermes wrote it about itself, after a
session where it hit exactly that `None` — you can watch it correct the bug mid-task and
then record why. The Pitfalls section is the whole idea of a self-improving agent, and it
is three bullet points long.

## It improves them by using them

This is the part usually described as magic, and is in fact a counter.

<MarginNote>
The counter counts tool-loop iterations rather than elapsed time — so a long
thinking pause does not trigger a review, but ten tool calls will.
</MarginNote>

Every tenth iteration of the tool loop, Hermes forks a background review of its own
recent work. That review follows a fixed editorial policy, and the policy has a
strong preference: patch a procedure that already exists rather than write a new
one. That single bias is why the library converges on a few good procedures instead
of sprawling into hundreds of near-duplicates.

<Depth min="operator">

The path runs through `agent/agent_init.py`, which sets `_skill_nudge_interval` to
10; `agent/conversation_loop.py`, which increments the counter once per iteration;
`agent/turn_finalizer.py`, which spawns the review at threshold; and
`agent/background_review.py`, which holds the editorial prompt itself.

</Depth>

When it revises a procedure, the old version does not vanish quietly:

<Revised
  was="Run the test suite. Do not proceed on failure."
  now="Run the test suite. Do not proceed on failure. Skip the browser tests — they are flaky on this machine and are covered in CI."
  why="Third run in a row where the browser tests failed locally and passed in CI"
  when="2026-07-14"
/>

That is what a self-improving agent actually looks like: a text file, revised, with
the reason recorded.

## What it remembers

Here the popular accounts are wrong, and the correction matters because it changes
what you can expect of it.

<Revised
  was="Hermes has a three-layer memory system: skill memory, conversational memory, and user modelling."
  now="Hermes keeps two small markdown files — MEMORY.md, capped at 2,200 characters, and USER.md at 1,375 — plus a full-text index of every past session that it searches on demand."
  why="Checked against the memory documentation. The three-layer framing appears in secondary sources, not in the docs"
  when="2026-07-25"
/>

Two files, both deliberately tiny, injected into the system prompt as a frozen
snapshot when the session starts. Everything else lives in a searchable index of
past conversations that Hermes queries when it needs to, rather than carrying it all
in context.

<ForTrack track="architect">

The cap is the control. Persistent memory is roughly 1,300 tokens by design, it is
human-readable, it sits at a known path, and `write_approval` can require review
before anything enters it. An agent whose long-term memory is two inspectable text
files is a fundamentally different governance proposition from one whose memory is
an opaque vector store.

</ForTrack>

## It delegates to copies of itself

Subagents start with no knowledge of the parent conversation at all — the
documentation is blunt about this, under a heading reading "Subagents Know
Nothing." Whatever a child needs, the parent passes explicitly. That sounds like a
limitation and is closer to a design decision: it keeps each child's context small
and its task legible.

## What this is not

It is not autonomous in the sense of unsupervised. It asks before dangerous
commands, refuses some outright regardless of your settings, and every one of those
guardrails can be switched off — which people do, occasionally with consequences
this guide comes back to.

It is also not something you configure once. It accumulates. That is the point, and
it is the thing to understand before pointing it at anything that matters.

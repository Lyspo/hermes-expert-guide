Hermes puts one line at the bottom of the terminal, and it is the most useful line
on the screen. Most people read the token count and ignore the rest, which is a
mistake — every field on it is telling you about a decision you are about to have
to make.

<Command verified="v0.19.0">hermes</Command>

Once a session is running, that line looks like this:

<Transcript label="Status bar, captured from a running v0.19.0" fidelity="verbatim" source="Captured session, 2026-07-25; model name replaced">
{`⚕ <model> │ 21.1K/1M │ [░░░░░░░░░░] 2% │ 42s │ ⏱ 7s`}
</Transcript>

Model, tokens against the window, the context bar, session elapsed, and turn elapsed.
The model name truncates past 26 characters.

Here the documentation and the software disagree, and it is worth knowing which to
trust:

The docs say cost reads `n/a` for models with no published price. What a real session
shows is the field missing altogether. Whether a priced provider restores it is
untested, so treat the cost figure as something to verify on your own install rather
than something to expect.

Two more states the documentation does not show. Before your first message, the
counters are placeholders:

<Transcript label="A fresh session, before the first turn" fidelity="verbatim" source="Captured session, 2026-07-25; model name replaced">
{`⚕ <model> │ ctx -- │ [░░░░░░░░░░] -- │ 1s │ ⏲ 0s`}
</Transcript>

And once a turn finishes, the live `⏱` freezes into `⏲` and a third badge appears,
counting up from the moment the answer landed:

<Transcript label="After a turn completes" fidelity="verbatim" source="Captured session, 2026-07-25; model name replaced">
{`⚕ <model> │ 76.9K/1M │ [█░░░░░░░░░] 7% │ 4m │ ⏲ 3m 52s │ ✓ 0s`}
</Transcript>

The `✓` badge is in no documentation page. Its value climbs after completion, so it
reads as time since the turn ended — useful for telling a finished agent from a stalled
one at a glance.

## The bar is a warning system with four states

The colours are fixed and worth memorising, because they map onto what you should
do rather than merely how full you are.

| Fill | Colour | What it means for you |
|---|---|---|
| Below 50% | green | Nothing to think about |
| 50–80% | yellow | Compression is now plausible; finish your thought |
| 80–95% | orange | Wrap up or compress deliberately |
| 95% and over | red | The documentation's own advice is "consider `/compress`" |

<MarginNote>
Fifty percent is not an arbitrary threshold. It is the default value of
`compression.threshold`, so green-to-yellow is the exact point at which automatic
compression becomes eligible to fire.
</MarginNote>

That last row is the one people meet unprepared. Nothing breaks at 95%, but your
options narrow: you can compress, or you can start a fresh session and lose the
thread.

## Compression costs money to save money

Compressing means sending the conversation to a model to be summarised, which is
tokens spent now to buy headroom later. What you are buying is the ability to continue
at all — and, because the summary re-establishes a stable prefix, cheaper turns from
that point on.

So a compression is not free, and if your install shows a cost field you should expect
it to rise across one. The captured session never compressed, which is why the replay's
compression frames are marked as the reconstructed part.

<Depth min="operator">

The defaults worth knowing, all under `compression` in `~/.hermes/config.yaml`:
`threshold: 0.50` sets when it fires, `target_ratio: 0.20` how far it compresses
down to, and `protect_last_n: 20` with `protect_first_n: 3` which messages are
exempt — the most recent twenty and the first three, so both your original framing
and your current thread survive intact.

One constraint is easy to get wrong, and the documentation is blunt about it: the
summary model "must have a context window at least as large as your main agent
model's." A smaller auxiliary model cannot read what it is being asked to summarise.

Editing `model.context_length` or any `compression.*` key on a running gateway takes
effect on the next message with no restart.

</Depth>

## The badges

After the first compression a counter appears, and it stays for the session:

<Transcript label="After compressing" fidelity="reconstructed" source="Badge glyph quoted from the TUI documentation; no compression occurred in the captured session">
{`⚕ <model> │ 38.2K/200K │ [██░░░░░░░░] 19% │ 10m │ ⏲ 52s │ 🗜️ 1`}
</Transcript>

The others you will meet: `▶ N` for active background tasks, `⏱` for live elapsed time
within a turn, `⏲` for the frozen figure once it ends, `✓` for time since the answer
landed, and `⚠ YOLO` when auto-approval is enabled.

That last badge is the only one that is a warning about you rather than about the
session, and module 4 is where it earns a lesson of its own.

## What to take from this

Read the bar as a budget, not a gauge. The tokens are what you have spent, the
colour is what you should do next, and the cost figure is the one number that goes
up when you fix the problem — which is the correct price for not losing your work.

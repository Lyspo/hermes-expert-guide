Self-improvement is the thing Hermes is sold on, and it is usually described as a disposition: the agent notices what worked and gets better at it. What actually ships is three mechanical parts — a counter, a threshold, and a second agent that is forbidden from speaking to you.

All three are small enough to hold in your head, and holding them is the difference between an agent that quietly improves and one that quietly gets strange.

01The counter counts iterations, not turns

Two configuration keys, both defaulting to ten: memory.nudge_interval and skills.creation_nudge_interval. The skill counter increments inside the tool-calling loop — once per API-call iteration, every time round. Not once per message you send.

That distinction is the whole behaviour of the loop.

The background review runs roughly every ten agent turns. It runs every ten tool-calling iterations. One request that takes five tool round-trips advances the counter by five, so a long piece of real work can trip it twice.

The increment sits inside the per-turn tool-calling loop and fires per API-call iteration; the curator documentation's “~every 10 agent turns” is an approximation of that count.
agent/conversation_loop.py:118 @ d372fda · corrected 2026-07-25

So the loop is not on a conversational clock. It is on a work clock. Ask three casual questions and it may never fire; ask the agent to trace a bug across six files and it will fire during that single request. This is the right design — the sessions worth learning from are exactly the tool-heavy ones — but it means the feature is close to invisible if you only ever chat.

Two more conditions gate the increment. The counter only advances while the skill_manage tool is actually available to the agent, and it resets whenever skill_manage is used. Edit a skill yourself and the clock starts again from zero.

02Your answer goes out first

At the end of the turn a finalizer checks three things: the counter has reached the interval, a final response exists, and the turn was not interrupted. Only then does it spawn the review.

The ordering is not incidental. The review never competes with your task for the model's attention and never delays your reply, because by the time it exists your reply has already been delivered. And because an interrupted turn produces no final response, hitting Ctrl-C on a run means nothing is learned from it.

03What you actually see

One line, after the answer, unprompted:

specimen · terminal outputVERBATIM

💾 Self-improvement review: Skill '<name>' created.

The published documentation shows this notice as 💾 Skill 'foo' patched. The real string is prefixed with Self-improvement review:, and on a fresh profile the observed verb was created rather than patched — which is what the review's own editorial policy predicts, since there was nothing yet to patch.

That single line is the only trace the loop leaves in your terminal. The counter is internal state and is never printed.

04The fork, and its four walls

The review is a daemon thread running a forked agent over a snapshot of your conversation. The module that implements it opens by describing itself:

Writes go straight to the memory + skill stores. Main conversation and prompt cache are never touched.

Four restrictions are set on that fork, and each one closes a specific door. A tool whitelist — its toolset is cut to the skills tools plus memory. Any other call is refused at runtime. It cannot read your files or reach the network, because it cannot call the tools that would.

_persist_disabled = True and _session_db = None. The fork shares your session id — deliberately, so it hits the same warm prompt-cache prefix — but it holds no handle to the session database and is barred from writing to it.

Approval auto-deny. Any dangerous-command approval callback the fork triggers is answered no on its behalf, and logged. There is no configuration that makes an unattended background review able to run a command that would have asked you first.
